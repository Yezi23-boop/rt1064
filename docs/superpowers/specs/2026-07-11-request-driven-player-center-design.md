# ART 请求式精确中心识别设计

> 状态：已实现。当前代码使用 `ART_REPLAN_INITIAL_CENTER` 和 `ART_REPLAN_SEGMENT_CENTER` 分离地图稳定与中心请求阶段。

## 目标

将 OpenART 的地图识别与小车精确中心识别彻底分开：普通运行只识别 16x12 字符地图，不查找或下发小车中心；只有 MCU 在关键停车节点发送 `CENTER_REQ` 后，OpenART 才临时识别精确中心并返回 3 个有效样本。

这样可以避免普通帧持续执行 `find_blobs()` 和逐像素精确扫描，降低中心识别对地图帧率的影响，同时保证发车、路径启动、推箱和返航等关键节点仍使用高精度中心。

## OpenART 普通模式

未收到中心请求时，每帧只执行：

```text
采集图像
-> 识别并稳定 16x12 字符地图
-> 发送 MAP_BEGIN、地图、PLAYER_CENTER_GRID 0,0 0、MAP_END
```

普通模式不调用：

- `detect_player_center()`。
- `detect_player_center_precise()`。
- 小车中心多帧滤波。

调试时可临时设置 `DEBUG_PLAYER_CENTER_ENABLE=True`，让普通帧额外执行中心检测、在 IDE 画十字并打印坐标。该开关默认关闭，且无论取值如何，普通地图 UART 都固定发送 `PLAYER_CENTER_GRID 0,0 0`，不会改变 MCU 的请求式中心流程。

字符地图中的 `C` 仍由网格采样点颜色分类产生，不依赖连续中心检测。保留 `PLAYER_CENTER_GRID 0,0 0` 行以维持现有地图帧协议格式，MCU 不再使用普通地图帧中心初始化或修正 pose。

## OpenART 请求模式

收到一条 `CENTER_REQ` 后进入请求模式：

1. 清空本轮请求样本计数。
2. 每个图像帧先寻找绿色和青色车身块的粗略 ROI。
3. 在 ROI 内执行逐像素精确中心识别。
4. 无有效精确中心时不发送样本，也不增加计数。
5. 每个有效帧最多发送一个样本：

```text
CENTER_SAMPLE 1,col_q,row_q
CENTER_SAMPLE 2,col_q,row_q
CENTER_SAMPLE 3,col_q,row_q
```

6. 第 3 个样本成功发送后退出请求模式，恢复普通地图识别。

重复收到新的 `CENTER_REQ` 时重新开始一轮 1、2、3 号样本。地图 UART 发送和请求响应继续复用现有 UART1，不增加新协议类型。

## MCU 统一请求流程

所有需要精确中心的状态统一执行：

```text
停车
-> 清空上一轮请求样本
-> 发送一次 CENTER_REQ
-> 等待 CENTER_SAMPLE 1/2/3
-> 对 col_q、row_q 分别取中值
-> 按当前 art_replan_phase 使用结果
```

MCU 当前状态决定中心用途，OpenART 不区分请求来源，因此无需增加 `CENTER_REQ LAUNCH` 等用途字段。

## 关键节点

以下节点必须使用请求式精确中心：

### 发车

5 秒启动等待结束后停车发送 `CENTER_REQ`。收满 3 个样本后计算当前 X，并生成到 `ART_LAUNCH_TARGET_X_CM` 的发车目标。发车流程不再读取普通 `PLAYER_CENTER_GRID`。

### ART 初次求解

真实推箱地图稳定且满足求解条件后，先保留当前稳定地图，再请求精确中心。收满样本后，根据该地图的 `C` 格计算初始 pose offset，随后调用 `solve_map()` 和 `executor_start()`。

### 单箱任务结束重规划

ART 稳定地图完成 B/T 数量确认后，停车请求精确中心。无论结果是 `Box OK` 还是 `Push Retry`，均在收满样本后用最新稳定地图计算新 executor 的初始 pose offset，再进行重算和启动。

### 连续推箱段开始前

保留当前 `PCtr` 行为：只在连续推箱段第一个大写 waypoint 前发送一次 `CENTER_REQ`。收满 3 个样本并修正 pose 后放行当前 waypoint，后续连续大写动作不重复请求。

### 返航

返航出口中心采样、Y/X 对齐前采样和最终 home 验证均改用 `CENTER_REQ`。返航流程不再读取普通地图帧中心。

## 等待与错误语义

所有关键节点采用与当前 `PCtr` 相同的等待规则：

- 没有有效中心时持续停车等待。
- 无效图像帧不计入 3 个样本。
- 不设置中心采样超时。
- 不因等待时间长而自动跳过、盲走或使用普通帧粗中心。
- K4 可取消当前 ART 流程并停车退出。

收满 3 个样本后，如果中心越界、与参考格不符或偏差超过配置阈值，则进入现有中心错误状态 `E:Ctr`，不继续运动。

## 状态显示

沿用现有 Execute 页状态文本，不增加页面或调试字段：

- `WCTR`：发车中心请求等待。
- `ICtr`：初次求解前中心请求等待。
- `RCtr`：单箱任务结束重规划前中心请求等待。
- `PCtr`：推箱前中心请求等待。
- `RetCtr` / `RetChk`：返航中心请求或验证等待。
- `E:Ctr`：样本收齐但校验或提交失败。

这些状态只复用 Execute 页现有状态文本位置，不新增影响地图显示区域的长期诊断行。

## 保持不变

- 16x12 字符地图识别与稳定帧判断。
- `MAP_BEGIN`、12 行地图、`PLAYER_CENTER_GRID`、`MAP_END` 的帧格式。
- BFS 求解、waypoint 语义和 B/T 数量确认。
- 编码器、yaw、位置环、速度环和 20cm 格距。
- 连续推箱段只在第一个大写 waypoint 前校正一次。
- 离线地图执行流程。

## 验证标准

- 普通帧不调用粗中心和精确中心检测函数。
- 普通地图帧固定发送 `PLAYER_CENTER_GRID 0,0 0`。
- 普通运行的 `LOOP_FPS` 比持续精确扫描时提高或至少不下降。
- 每条 `CENTER_REQ` 只产生一轮有序的 1、2、3 号有效样本。
- 发车、初次求解、任务重规划、推箱前和返航均不依赖普通帧中心。
- 所有中心等待均无自动超时，K4 仍能立即停车退出。
- 收不到中心时车辆保持停止；收满并通过校验后才继续对应流程。
- OpenART Python 语法和请求协议测试通过。
- MCU 主机测试通过，Keil 编译为 `0 Error(s), 0 Warning(s)`。
