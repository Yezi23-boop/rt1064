# OpenART 唯一小车格地图设计

## 背景

OpenART 当前按 16x12 网格逐格识别元素。小车颜色覆盖相邻采样点时，稳定字符地图可能同时出现多个 `C`；小车格识别短暂丢失时，也可能出现零个 `C`。普通周期地图不携带精确中心，MCU 会发布这类地图，导致 `art_replan`、`subject2`、solver 和屏幕对多个 `C` 采用不同处理方式。

本设计把唯一小车格的决定权放在 OpenART。OpenART 只向 MCU 发布恰好包含一个小车格的规范地图；MCU 不再从多个 `C` 中猜测位置，只负责校验并拒绝非法帧。

地图中的 `C` 表示小车位于普通地面，`+` 表示小车位于目标点。本文所称“小车格数量”均指 `C` 与 `+` 的总数。

## 目标

- OpenART 下发的每张完整业务地图必须恰好包含一个 `C/+`。
- 原始地图恰好识别出一个 player 时继续走现有高速路径，不启动精确中心识别。
- 原始地图出现零个或多个 player 时，利用历史位置作为搜索锚点，按需启动现有精确小车中心识别。
- 精确中心成功后，根据中心所在网格生成唯一 `C/+`，不把原始多个 `C` 交给 MCU。
- 精确中心失败时不发布非法新地图，MCU 继续使用上一张合法快照。
- 保留车压目标时的 `+` 语义，并正确恢复小车离开后的 `T`。
- `CENTER_REQ` 和 `OBSERVE_REQ` 的请求式精确中心协议保持现有语义。

## 非目标

- 不修改小车颜色阈值、透视标定、网格尺寸或地图字符协议。
- 不让 MCU 在多个候选 `C` 中选择最近格或第一个格。
- 不要求普通唯一 C 帧每次都运行精确中心识别。
- 不修改 BFS、executor、PID、里程计或科目一/科目二业务状态机。

## 总体流程

OpenART 每帧完成现有逐格识别和稳定滤波后，统计稳定地图中的 player 数量。

```text
生成稳定字符地图
        |
        v
统计 player 数量
        |
   +----+----+
   |         |
恰好 1 个   0 个或多个
   |         |
快速发布     选择历史搜索锚点
   |         |
更新历史     运行精确中心识别
             |
        +----+----+
        |         |
      成功       失败
        |         |
生成唯一 C/+   本帧不发布
更新历史       下一帧重试
```

## 唯一 C 快速路径

稳定地图中 `player_count == 1` 时：

1. 直接将该 player 格作为本帧唯一小车格。
2. 不调用 blob 精确中心识别，保持当前高速帧率。
3. 用该格的图像采样中心更新粗搜索锚点和最后有效 row/col。
4. 生成规范地图并发送。
5. 普通快速帧没有精确中心时继续发送 `PLAYER_CENTER_GRID 0,0 0`，不得把格中心伪装成精确中心。

这一分支服从用户指定的直接策略，不额外加入位置跳变门控。

## 零 C 与多 C 恢复路径

稳定地图中 `player_count != 1` 时，不直接发送该字符地图，而是启动现有小车精确中心检测。

搜索锚点按以下顺序选择：

1. 上一次成功识别的精确小车像素中心。
2. 上一次唯一 C 所在格的图像采样中心。
3. 当前多个 player 候选中距离历史锚点最近的候选格中心。
4. 没有任何历史锚点时，本帧不发布，等待后续帧先建立有效小车位置。

历史 C 只用于限定图像搜索区域，不能直接作为本帧最终小车位置。精确中心成功后，使用现有 `player_center_to_grid_q()` 转换为 `col_q/row_q`，再计算：

```text
car_col = col_q / 100
car_row = row_q / 100
```

只有中心位于 16x12 地图范围内时才能生成规范地图。成功后更新精确中心、粗锚点和最后有效 row/col。

## 背景格恢复

OpenART 维护一份 16x12 的最近非小车背景。某格本帧可靠识别为非 player 时，更新该格背景；识别为 player 时保留原背景。

生成规范地图时：

- 清除所有原始 player 候选。
- 未被选中的候选格恢复为最近非小车背景。
- 选中格的背景为 `T` 时写入 `+`。
- 选中格的其他可通行背景写入 `C`。
- 不能把未选中的候选格一律写成 `.`，避免误删墙、目标或障碍。

背景尚未建立且无法确定候选格原内容时，不发布该异常帧。首张合法地图必须由唯一 C 快速路径或具有可靠背景的精确中心路径建立。

## 发送契约

OpenART 在调用 `send_map_uart()` 前完成规范化。下发顺序保持不变：

```text
MAP_BEGIN
<12 行规范地图，C/+ 总数恰好为 1>
PLAYER_CENTER_GRID col_q,row_q valid
MAP_END
```

- 唯一 C 快速路径没有精确中心：发送 `PLAYER_CENTER_GRID 0,0 0`。
- 零 C/多 C 恢复成功：发送本帧真实精确中心和 `valid=1`。
- 恢复失败：整张 MAP 帧不发送，不能发送零 C、多个 C 或旧 C 拼接新 B/T 的地图。
- `CENTER_REQ` 仍按现有方式返回多帧精确中心样本，不受普通周期快慢路径影响。
- `OBSERVE_REQ` 仍返回小车中心与箱子中心配对样本，不受本设计影响。

## MCU 防御校验

MCU 在完整 `MAP_END` 到来后、发布快照之前统计 `C/+`：

- 恰好一个：发布地图并递增 frame count。
- 零个或多个：拒绝整帧，不更新地图快照、中心、frame count 和 B/T 基线。

MCU 不从非法帧中选择第一个 C，也不把旧 C 注入包含新 B/T 的地图。现有 `normalize_staging_player_from_center()` 可保留为目标底色恢复和协议防御，但正常业务帧应已由 OpenART 保证唯一 C。

`art_replan`、`subject2`、solver 和 screen 只读取 MCU 发布的规范地图，因此它们不再需要各自定义多个 C 的业务策略。

## 性能策略

- 正常唯一 C 帧只增加一次 12x16 计数和规范地图生成，开销可忽略。
- blob 精确中心识别只在零 C 或多 C 的异常帧运行。
- 精确中心连续失败不会发送无效地图，也不会增加 MCU 的稳定地图计数。
- 不增加普通帧 UART 数据量，协议行数保持不变。

## 错误处理

- 精确中心识别失败：保留历史锚点，本帧不发，下一帧重试。
- 精确中心越界：视为识别失败，本帧不发。
- 无历史锚点且零 C：等待后续唯一 C，不盲目全图猜测。
- MCU 收到非法 C 数量：丢弃整帧并保留上一张合法快照。
- 长时间无法生成合法地图时，上层沿用现有 Wait Map/ART timeout 行为，本设计不新增运动降级。

## 验证

OpenART Python 测试至少覆盖：

- 唯一 player 走快速路径，不调用精确中心检测。
- 零 player 使用旧精确中心或旧 C 作为搜索锚点。
- 多个 player 不直接选择第一个候选。
- 精确中心成功后只保留对应格的唯一 `C/+`。
- 车位于目标时输出 `+`，离开后恢复 `T`。
- 未选候选恢复最近非小车背景，不把墙改成空地。
- 精确中心失败时不调用周期地图发送。
- 普通快速帧中心 `valid=0`，精确恢复帧中心 `valid=1`。

MCU 主机测试至少覆盖：

- 唯一 `C` 和唯一 `+` 帧正常发布。
- 零 C、两个 C、`C+` 同时存在均拒绝整帧。
- 拒绝帧不改变旧地图、frame count、配套中心和 B/T 基线。
- 合法请求式中心帧仍能恢复目标底色并发布唯一小车格。

完成前运行 OpenART Python 测试、对应 UART 主机测试、全量主机测试、Python 语法检查和 Keil 编译，要求固件达到 `0 Error(s), 0 Warning(s)`。

## 假设

- OpenART 能在已有历史锚点附近可靠运行当前精确小车中心算法。
- 小车正常运动过程中绝大多数稳定帧能够得到一个粗 player，因此异常精确路径不会长期占用算力。
- 上位机地图中的墙、箱子、目标和障碍仍由现有颜色识别提供；本设计只规范小车格。
- 比赛流程允许 MCU 在短暂视觉异常时继续保留上一张合法地图，而不是接收一张没有可靠小车位置的新地图。
